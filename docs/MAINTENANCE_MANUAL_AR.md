# دليل الصيانة والتشغيل الآمن — أسناني قطر / MMC-MMS

> **الغرض:** هذا هو الملف المرجعي لصيانة التطبيق بعد النشر. يوضح من يفحص ماذا، ومتى، وكيف يثبت النتيجة، ومتى يتوقف بدل المخاطرة بالبيانات أو الميزانية. لا يغير هذا الدليل عقد المنتج؛ ارجع إلى [README الجذري](../README.md) للعقود، و[دليل النشر](DEPLOYMENT_RUNBOOK.md) لتسلسل الاستضافة، و[سجل الحالة](CURRENT_PRODUCTION_STATUS.md) للحكم القائم.
>
> **قاعدة غير قابلة للتفاوض:** لا تنشأ بيانات اختبار أو حجز أو OTP أو حمل أو concurrency في Production. الكتابة والـfixtures وK6 تخص Staging المعزول فقط، وبوسم `TEST_STG` ثم تنظيف موثق.

## 1. مصفوفة المسؤوليات

| الدور | ما يملكه | ما لا يملكه |
|---|---|---|
| مشرف الصيانة/المنصة | فحص CI والنشر والسجلات وadvisors والـrollback وتحديث الحالة. | لا يضع أسرارًا في Git أو ينشئ بيانات اختبار Production. |
| مدير المنصة | حوكمة العيادات والكتالوج والـfeature flags والتقارير ضمن الواجهة. | لا يتخطى سجل التحقق لتفعيل مركز أو فرع أو ممارس. |
| المدير الأعلى | إدارة حسابات المرضى والعملاء التشغيليين عبر المسار المصرح، مع أثر تدقيقي. | لا يشارك كلمات المرور أو claims أو service key. |
| مالك العيادة | تشغيل عيادته وإنشاء/إلغاء حسابي عميل تشغيلي كحد أقصى عند استيفاء الشروط. | لا يمنح إدارة منصة أو وصولاً لعيادة أخرى. |
| مطور/مراجع | تعديل المصدر والترحيلات واختبارات Staging ومراجعة PR. | لا يطبق DDL بعيدًا بلا migration ولا يدفع ملفات مولدة/أسرار. |

## 2. دورة الصيانة

| التواتر | الإجراء | الدليل المطلوب | حد التوقف |
|---|---|---|---|
| عند كل تغيير مصدر | `git diff --check` ثم `npm run verify`. | نتيجة نظيفة؛ التحذيرات القائمة توثق ولا تخفى. | أوقف النشر عند error أو تغير غير مقصود. |
| قبل دمج `main` | راجع `git status`، الملفات المتتبعة فقط، وAGENTS/README. | commit قابل للمراجعة ومحدود النطاق. | لا تدفع `.env*` أو artifacts أو dumps أو ملفات `.next/`. |
| بعد نشر Production | تحقق read-only من `READY`، الصفحة العامة، البحث العام، و`/api/health`، ثم شغل `production-readiness-check.mjs` على النطاق المنشور. | رابط deployment ووقت الفحص وتقرير البوابة؛ لا يتضمن التقرير أسراراً أو بيانات مستخدمين. | لا تسجل/تحجز/تجرب OTP أو K6 في Production. |
| بعد تغيير DDL أو grants | طبق migration مصدرية في البيئة المقصودة، ثم افحص SQL read-only وSecurity Advisor. | رقم migration وpostconditions واضحة. | لا تعتبر rollback للنشر عكسًا لقاعدة البيانات. |
| أسبوعيًا أو بعد حادث | راجع runtime errors وSecurity/Performance Advisor. | ملخص alert ورابط remediation إن وجد. | لا تحذف index لمجرد `unused` INFO. |
| قبل أو بعد fixture Staging | عدادات TEST_STG قبل/بعد، ثم حذف متسلسل للجداول التابعة والحسابات والجلسات. | نتائج صفرية للحسابات والملفات والعضويات والعروض والمواعيد والحجوزات الموسومة. | لا تستعمل أسماء أو بريدًا أو بيانات من Production في fixture. |

## 3. قائمة تحقق قبل النشر وبعده

### قبل النشر

1. تؤكد هوية الفرع والبيئة: `staging` لاختبارات الكتابة و`main` للإصدار الموثق فقط.
2. تشغل `npm run verify` وتراجع `git diff --check`.
3. تراجع أن أي تغيير DDL يقع في `supabase/migrations/` وأنه لا يعدل migration مطبقة.
4. تراجع أن العقود تحدثت في README، وأن هذه الوثيقة وفهرس المصادر تحدثا عندما تتغير المسؤوليات أو التشغيل.
5. تفحص عدم وجود أسرار أو بيانات مرضى أو cookies أو screenshots حساسة أو ملفات مولدة في diff.
6. عندما يحتاج Playwright إلى إعداد Supabase local، لا تنسخ مفتاح Production أو Staging إلى shell أو Git؛ النتيجة حينها **blocked محليًا** وليست ترخيصًا لتجاوز السرية.

### بعد النشر

1. طابق commit مع deployment في Vercel وتأكد من `READY`.
2. افحص `GET /api/health` والصفحة والبحث العام فقط.
3. راجع runtime errors الخاصة بالdeployment الجديد؛ لا تنسب مجموعة خطأ تاريخية للإصدار الجديد بلا وقت/commit مطابقين.
4. بعد migration راجع grants لدوال `_server`: لا يجوز لـ`anon` أو`authenticated` تنفيذها.
5. حدّث `CURRENT_PRODUCTION_STATUS.md` إذا تغير الإصدار أو الحكم أو حاجز مثبت، و`REMOTE_APPLIED_MIGRATIONS.md` إذا طبقت migration عن بعد.

## 4. صيانة Staging والـfixtures

### 4.1 إنشاء fixture

| القاعدة | التطبيق |
|---|---|
| تسمية واضحة | استخدم `TEST_STG` في الاسم القانوني أو البيان المناسب، وبوادئ بريد/username مخصصة. |
| عزل | استخدم Supabase Staging `yrlwoxlxizxgrodtbdcp` وPreview المرتبط بـ`staging` فقط. |
| بيانات دنيا | أنشئ أقل عدد من الحسابات والعروض والمواعيد اللازمة للاختبار. |
| إثبات الحراس | لا تزيف سجل تحقق لتفعيل عيادة/فرع أو OTP؛ إن منع الحارس المسار فهو نتيجة صحيحة. |
| أسرار قصيرة العمر | احفظ cookie أو password تجريبي في ذاكرة/ملف خاص محمي مؤقتًا فقط، ولا تطبعه ولا تدفعه. |

### 4.2 تنظيف fixture

رتب الحذف من الأثر التابع إلى الأصل: notifications/history/audit المرتبط، ثم booking/slot/offer عند وجودها، ثم operator events/accounts/memberships، ثم challenges/profiles/usernames/profiles، ثم مستخدم Auth، وأخيرًا branch/clinic. يراعى ترتيب foreign keys الفعلي في المخطط.

بعد الحذف، نفذ عدادًا تجميعيًا فقط يثبت صفر: المستخدمين، ملفات المرضى، usernames، memberships، operator accounts/events، العيادات والفروع، سجلات التحقق، العروض والكتالوج والأنواع، المواعيد والحجوزات الموسومة، و`booking_status_history` و`booking_attendance_events` و`notification_outbox` ومحاولات تسليمها التابعة أو اليتيمة. امسح جلسة المتصفح وsessionStorage وملفات K6 الخاصة. لا تحذف bucket rate-limit عام مشترك لمجرد أنه من نفس الجهاز؛ احذف فقط المفتاح المشتق من subject الاختباري المعروف.

عند تعديل سياسة قراءة `bookings` أو `patient_profiles`، اختبر في Staging بدور `authenticated` وclaim العميل المقيد. لا تجعل سياسة الحجز تستعلم `patient_profiles` تحت RLS إذا كانت سياسة الملف التشغيلي تستعلم `bookings`؛ استخدم حارسًا خاصًا محدود التنفيذ للحالات الذاتية مثل الحساب المؤرشف، ثم أثبت أن العميل يرى فروعه وحجوزاته المصرح بها فقط. لا تترك سياسة permissive قديمة موازية لسياسة موحدة جديدة: افحص `pg_policies` قبل وبعد كل migration، واضمن أن القراءة الذاتية بعد الأرشفة غير متاحة وأن وصول الفرع المصرح يبقى مقيداً بالحجز المرتبط.

## 5. K6 والأداء

| الإجراء | مسموح؟ | الشروط |
|---|---|---|
| `search-flow.js` في Staging | نعم | `TARGET_ENV=staging` و`LOAD_TEST_CONFIRMATION=STAGING_ONLY` وHTTPS وrun id صالح. |
| `booking-flow.js` في Staging | نعم عند توفر fixture | إضافة إلى الحراس السابقة: `BOOKING_WRITE_CONFIRMATION=STAGING_TEST_DATA_ONLY` وfixture خاص وcookie قصير العمر. |
| `booking-integrity-flow.js` في Staging | نعم عند توفر fixture | جميع حراس الحجز، مع `BOOKING_INTEGRITY_MODE=retry` لاختبار مفتاح واحد يعيد كود الحجز نفسه، أو `BOOKING_INTEGRITY_MODE=concurrency` لعدة حسابات مختلفة على slot/offer واحد؛ ينجح إنشاء واحد فقط والبقية `409`. |
| K6 أو stress أو booking race في Production | **ممنوع** | لا استثناء في هذا الدليل. |
| ادعاء سعة 50,000 مستخدم | غير مسموح بلا دليل موزع | يلزم خطة حمل موزع وقياسات تكلفة/حدود وبنية موافق عليها؛ لا تستنتجها من smoke محلي. |

إذا كانت Staging خالية من عيادة/فرع/عرض/موعد حقيقي ومتحقق منه، يسجل الاختبار **BLOCKED** ولا تنشأ تفعيلات اصطناعية لتجاوزه. يتطلب المشغل إدخال البيانات المصرح بها في Staging أولًا. لا يحاكي الاختبار إرسال OTP ولا يملأ `phone_verified_at` كدليل رسالة؛ يظل ذلك مقيداً بمزود حقيقي مهيأ وموافقة تشغيلية منفصلة.

## 6. الحوادث والاستعادة

| شدة | أمثلة | الإجراء الأول | ما يوثق |
|---|---|---|---|
| حرجة | تسريب محتمل، منح RPC عام، تعطل حجز واسع، خطأ migration. | أوقف التغيير اللاحق، اعزل المسار، راجع السجلات وAGENTS ودليل الحوادث. | الوقت، البيئة، commit، الأثر، الإجراء والتعافي. |
| عالية | فشل نشر، 5xx لمسار حرج، ناتج بحث غير صحيح. | قارن deployment والـruntime errors، ثم أصلح على branch واختبر Staging. | request/route آمن، commit، نتيجة smoke. |
| متوسطة | مكوّن UI لا يحمّل أو INFO advisor. | أنشئ مهمة مقيّدة، لا تخلطها بإصدار حرج. | السبب، النطاق، قرار الأولوية. |
| منخفضة | تحسين نص أو فهرس غير مستخدم. | وثق ثم عالج في دورة صيانة. | تبرير عدم المخاطرة. |

لا تستخدم rollback للنشر لعكس migration. عند الحاجة إلى عكس أثر SQL، أضف migration عكسية مصدرية ومراجعة، ثم طبقها في Staging قبل Production. يظل [دليل الاستجابة للحوادث](INCIDENT_RESPONSE_AND_RECOVERY_AR.md) مرجع تفاصيل الاستجابة؛ هذا الدليل يحدد نقطة الدخول اليومية فقط.

## 7. صيانة الأمن والأسرار

1. تمنع `AGENTS.md` وضع secrets وJWT وcookies وdumps في Git أو التوثيق أو screenshots.
2. افحص `npm run predeploy:check` ضمن `npm run verify`؛ لا تستبدله بمراجعة بصرية.
3. يبقى `SUPABASE_SECRET_KEY` وبديله legacy للخادم فقط؛ لا تستورده مكونات client.
4. لا تمنح `_server` إلى `anon` أو `authenticated`. يبقى الاستثناء العام للبحث فقط بأقل صلاحيات.
5. إذا ظهر Advisor يحوي تغيير خطة/تكلفة، لا تشتري أو ترقي. سجّل الحاجز وارفعه للمشغل لاتخاذ قرار صريح.
6. لا تفعّل SMS/OTP أو خدمة نموذج خارجية بقيم تجريبية؛ غيابها يجب أن ينتج فشلًا آمنًا.

## 8. صيانة الوثائق ومنع التكرار

| نوع المعلومة | مصدر واحد إلزامي | متى يحدّث |
|---|---|---|
| عقود المنتج والمسارات وAPI | `README.md` | مع أي تغيير سلوك/contract. |
| خريطة الكود والطبقات | `ARCHITECTURE_AND_CODE_MAP_AR.md` و`SOURCE_MANIFEST.md` | مع نقل/إضافة مسؤولية أو ملف محوري. |
| استخدام الأدوار | `operations-manual/OPERATIONS_MANUAL_AR.md` | مع زر أو دور أو حالة أو صلاحية جديدة. |
| الصيانة والنشر والحوادث | هذا الملف و`DEPLOYMENT_RUNBOOK.md` | مع تغيير بوابة جودة أو استضافة أو rollback. |
| الحالة الحية | `CURRENT_PRODUCTION_STATUS.md` | مع نشر أو postcondition أو blocker جديد. |
| سجل schema البعيد | `supabase/REMOTE_APPLIED_MIGRATIONS.md` | بعد تطبيق migration والتحقق منها عن بعد. |
| تقرير مؤرخ | `docs/` التاريخية | فقط عندما يكون دليلًا مستقلًا بزمن/بيئة، ولا يعاد تحريره لإعادة كتابة الماضي. |

قبل حذف ملف متتبع، أثبت أنه مكرر **حرفيًا** أو أن مرجعًا حاكمًا حل محله، وافحص كل الروابط إليه. لا تحذف تقريرًا تاريخيًا لمجرد أنه قديم. أما artifacts غير المتتبعة و`.next` وtest results وملفات Supabase المؤقتة فتزال من مساحة العمل ولا تدخل commit.

## 9. أوامر آمنة مرجعية

```bash
# تحقق المصدر من دون أسرار
npm run verify

git diff --check
git status --short

# مراجعة ملفات متتبعة فقط
git ls-files

# فحص جاهزية Production قراءة فقط:
node scripts/production-readiness-check.mjs https://www.mmc-mms.com

# لا تشغل هذه على Production:
# k6 run load-tests/k6/booking-flow.js
# k6 run load-tests/k6/booking-integrity-flow.js
```
