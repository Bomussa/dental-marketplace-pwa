## ما لا يثبت هذا الإصدار

لا يُنشئ الفحص الإنتاجي أي مريض أو حجز أو موعد أو account اختبار، ولا يشغل K6 أو stress/concurrency على Production. حجية تكامل الحجز والـsnapshot والسعر وidempotency والسباق وIDOR مستمدة من Staging المعزول فقط. كذلك لم يُثبت إرسال OTP حقيقي، لأن تهيئة Twilio Verify غير موجودة ولا يُضاف مزود مدفوع ضمن شرط الكلفة الصفرية.

## القيود والحواجز

| العنصر | الحالة المطلوبة |
|---|---|
| OTP/SMS الحقيقي | **BLOCKED** حتى يوفر المشغل تهيئة مزود الرسائل ثم يعاد اختبارها بموافقة ونطاق آمن. لا يعتبر `phone_verified_at` الاصطناعي في Staging إثباتًا لرسالة حقيقية. أزيلت SMS من **إشعارات الحجز** فقط واستبدلت بإشعار `in_app`؛ لم يُلغ حاجز OTP من الحجز. |
| واجهة العميل التشغيلي | **PASS في Preview Staging**: أُنشئ حساب TEST_STG عبر التسجيل الحقيقي، وربط بعضوية receptionist مقيّدة بالفرع و`clinic_bookings_only`. بعد إصلاح RLS رأى الفرع Alpha فقط وحجزين مقيدين، وأثبتت الواجهة تأكيد الحجز والحضور والإكمال، وأعاد الحارس كل المسارات غير المصرح بها إلى `/clinic/bookings`. لم يُكشف أي سر أو PII في التوثيق، وأزيل الحساب والعضوية والعيادتان والفروع والحجوزات والتاريخ والحضور والإشعارات التابعة جميعًا بعدادات صفرية موسعة. |
| K6 booking/retry | **BLOCKED — لا تنفيذ كتابي**: السيناريو وحراسه المحليون موجودون ويشترطون `TARGET_ENV=staging` وHTTPS وfixture خاصًا. رفض التشغيل قبل أي طلب HTTP لأن fixture غير موجودة، والفحص الحي لـStaging أعاد صفر عيادات/فروع/كتالوج/عروض/مواعيد نشطة قابلة للحجز. لم تُختلق verification أو activation لتجاوز الحارس؛ لذلك لا يوجد ادعاء تحمل أو سعة 50,000 مستخدم. |
| المواعيد التشغيلية | يتطلب تنفيذ K6 الفعلي إدخال/نشر عيادات وعروض ومواعيد **حقيقية ومتحققًا منها من المشغل المخول** في Staging أولاً، ثم إنشاء fixture TEST_STG منعزل وتنظيفه. لا تُنشأ بيانات وهمية أو تفعيلات غير متحققة في Production. |
| حماية كلمات المرور المسرّبة | **WARN / BLOCKED بقرار مالك**: يثبت المستشار أن الإعداد معطل، ووثائق Supabase الحالية تقصره على خطة Pro وما فوق. لا تُفعّل ترقية أو شراء أو إعداد Production Authentication تلقائياً ضمن شرط $0. |

## قواعد الرجوع والتشغيل الآمن

إذا ظهر فشل حرج بعد هذا الإصدار، يؤكد المشغل أولاً نشر Production السابق الموسوم `READY` والمرشح في Vercel في وقت الحادث، ثم يعيد التوجيه إليه ويعالج المصدر في فرع ويختبره في Staging قبل دفع `main` جديد. لا تثبت هذه الوثيقة مرشحاً ثابتاً لأن قائمة المرشحين تتغير مع النشر. لا تستخدم rollback للنشر كبديل لعكس DDL: ترحيلات المخطط الحالية تحتاج migration مصدرية أمامية صريحة إذا تطلب الرجوع تغييرًا في قاعدة البيانات.

لا تضع مفاتيح أو JWT أو كلمات مرور أو dumps في Git أو الوثائق أو logs. لا تُطبق DDL مباشرةً خارج migration مصدرية، ولا تجرّب الحجز/OTP أو الضغط في Production.
