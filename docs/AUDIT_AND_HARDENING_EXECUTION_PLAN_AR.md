# خطة التدقيق الواسع والتحصين والإصدار — أسناني قطر / MMC-MMS

## الهدف

إجراء مراجعة هندسية واسعة ومنهجية لتطبيق **أسناني قطر / MMC-MMS** عبر الكود والواجهات والعقود وقاعدة البيانات وطبقة Realtime والنشر، ثم إصلاح **العيوب المؤكدة القابلة لإعادة الإنتاج فقط**، واختبار الإصلاحات، ودفع الإيداعات إلى GitHub والتحقق من وصولها إلى إنتاج Vercel. الهدف هو تقليل احتمالات الكسر والتعارض والازدواجية، وليس ادعاء أن أي نظام يمكن إثبات خلوه نظرياً من كل خطأ مستقبلي.

> **حدود ثابتة:** لن يُنشأ حجز أو سجل مريض أو رسالة SMS حقيقية ضمن الاختبارات العامة، ولن يُنفذ حمل مرتفع على الإنتاج. اختبارات الضغط والحجز المتزامن ستستخدم بيئة معزولة أو Preview وبيانات اختبار آمنة ومفاتيح idempotency مخصصة، وبسقف متدرج ومراقب.

## المرحلة 1: تثبيت خط الأساس القابل للمقارنة

1. أتحقق قراءةً فقط من نظافة شجرة Git، والإيداع المحلي والبعيد، وحالة أحدث نشر في Vercel، ونتائج أخطاء runtime خلال نافذة زمنية محددة.
2. أراجع صحة النطاقين وHTTPS والتحويل و`/api/health` ورؤوس الحماية، من دون كتابة بيانات.
3. أطابق ملفات الترحيل المحلية مع سجل الترحيلات البعيدة، وأتحقق من تزامن `database.types.ts` مع الدوال والجداول التي تستهلكها طبقة التطبيق.
4. أسجل نقطة البداية في تقرير مؤرخ؛ لا أغير وثائق أو كوداً في هذه المرحلة إلا إذا كان السجل نفسه يحتوي معلومة تشغيلية مؤكدة خاطئة.

**معيار الخروج:** سجل خط أساس يبين الإيداع، حالة النشر، صحة الخدمة، ومجالات التدقيق من دون أي طفرة بيانات.

## المرحلة 2: التدقيق الواسع المتوازي

ستنفذ المسارات التالية بالتوازي المنهجي قدر استقلالها، ثم تدمج نتائجها في قائمة واحدة مرتبة حسب الشدة والأثر وقابلية إعادة الإنتاج.

| المسار المتوازي | نطاق التدقيق | مخرجات القبول |
|---|---|---|
| A — العقود والمسارات | كل صفحات App Router وRoute Handlers وServer Actions، نماذج Zod، تطبيع الإدخال، أخطاء JSON، رموز الحالة، والـredirect الآمن. | جدول يغطي كل مسار وطلبه وصلاحيته وتحويلاته، مع حالات حافة قابلة للاختبار. |
| B — قاعدة البيانات والحجز | الترحيلات، RLS، grants، RPCs، `SECURITY DEFINER`، idempotency، انتقالات الحجز، الفهارس، والقيود التي تمنع التكرار أو الحجز المتزامن. | خريطة من الإجراء الخادمي إلى RPC وسياسة RLS واختبار SQL/وحدة أو توصية مبررة. |
| C — الواجهة وRealtime والأدوار | البحث والمقارنة، الترجمة واتجاه RTL/LTR، PWA/offline، Realtime وإعادة الاتصال، ولوحات المريض والعيادة والإدارة حسب الدور. | قائمة مسارات المستخدم، وما يراه كل دور، وحالات عدم توفر الشبكة أو الموقع أو البيانات. |
| D — التحصين والاعتمادية | حارس الكتابة العامة، origin/body limits/rate limits، الرؤوس، CSP، الأسرار، التبعيات، ورفض الوصول إلى تقارير الإدارة والكتابات الحساسة. | نتائج ثابتة للطلبات غير الموثوقة، وفحص تبعيات الإنتاج، وعدم كشف رسائل داخلية أو أسرار. |
| E — الاختبار والمراقبة | تحليل فجوات Vitest وPlaywright واختبارات SQL، مراجعة سجلات runtime وبناء Vercel، وتحليل قياس أداء خفيف متعدد المراحل. | مصفوفة: «مغطى / غير مغطى / يحتاج بيئة مخولة»، مع حالة مراقبة النشر والأخطاء. |

**قرار الدمج:** لا تتحول الملاحظة إلى إصلاح إلا عند وجود دليل من الكود أو اختبار فاشل أو استجابة حية قابلة للتكرار. تُصنّف النتائج إلى حرجة أو عالية أو متوسطة أو ملاحظة تحسين، ويبدأ العمل بالحرجة ثم العالية.

## المرحلة 3: إصلاحات دقيقة ومنع الرجوع

1. أعزل كل عيب مؤكد في إيداع صغير قابل للمراجعة، من دون إعادة كتابة شاملة أو تغيير سلوك غير مرتبط بالمشكلة.
2. أحافظ على مصدر حقيقة واحد: عقود الإدخال في `lib/validation.ts`، العمليات ذات الامتياز في `lib/operations.server.ts` وRPCs/الترحيلات، ومنطق العرض في المكونات المشتركة.
3. أضيف أو أعدل الاختبار الذي يثبت العيب أولاً، ثم أصلح أقل طبقة صحيحة (قاعدة البيانات أو الخادم أو العقد أو الواجهة) وأعيد الاختبار.
4. لا أستخدم صلاحية العميل لحماية عملية حساسة، ولا أفتح سياسة RLS أو أضيف مفتاحاً عاماً أو أضع سراً في المستودع كحل سريع.
5. إذا استلزم الإصلاح ترحيلاً، أنشئ ترحيلاً تقدمياً آمناً مع فهارس وسياسات/منح مقصودة، وأتحقق من أثره قبل ربطه بالواجهة.

**معيار الخروج:** لا يوجد إصلاح بلا اختبار منع رجوع، ولا تغيير واسع غير مبرر، ولا بيانات أو رسائل حقيقية ولّدها التدقيق.

## المرحلة 4: التحقق متعدد الطبقات

| الطبقة | إجراءات القبول |
|---|---|
| ثابتة ومحلية | `git diff --check`، `npm run predeploy:check`، TypeScript، ESLint، وفحص الأسرار المدمج. |
| منطق وعقود | `npm run test`، واختبارات وحدة إضافية لعقود البحث والحجز والحراسة والصلاحيات والتقارير بحسب الإصلاحات. |
| قاعدة البيانات | اختبارات القبول SQL وقراءات الترحيلات/RLS والدوال ذات الصلة، مع سباقات حجز على بيانات اختبار معزولة فقط عند الحاجة. |
| المتصفح | `npm run test:e2e` على سطح المكتب والهاتف، مع البحث واللغة ورفض المسارات الحساسة وPWA، وإضافة حالات موثقة للأدوار عند توفر حسابات اختبار مخولة. |
| الضغط والأداء | تشغيل `scripts/safe-load-test.mjs` أو خطة اختبار معزولة مع صعود تدريجي ومراقب، وقياس `p50/p95/error rate` من المصدر الملائم. لا يفسر زمن شبكة واحد على أنه عيب كود، ولا ينفذ حملاً مؤذياً على الإنتاج. |
| الإنتاج بعد النشر | تحقق قراءة فقط من النطاقين، `api/health`، الرؤوس، مسارات البحث العامة، ورفض الطلبات غير الموثوقة، ثم مراقبة Vercel للأخطاء وحالة النشر. |

## المرحلة 5: الإيداع والنشر والتوثيق

1. أراجع كل فرق، وأحدّث README ودليل النشر وكتيب التشغيل وسجل الترحيلات/فهرس المصادر فقط عندما يغير الإصلاح عقداً أو سلوكاً أو قيداً فعلياً.
2. أضيف التغييرات ذات الصلة، وأعمل إيداعات وصفية قابلة للتتبع، ثم أدفعها إلى `main` في GitHub كما طلب المستخدم.
3. أراقب أحدث نشر Vercel باستخدام معرف الفريق الموثق `team_aFtFTvzgabqENB5bOxn4SiO7` حتى يصل إلى `READY` أو أستخرج سجلات البناء لمعالجة فشل مثبت.
4. أسلم تقريراً مختصراً يذكر الإيداعات، ما فُحص، العيوب التي أصلحت، الاختبارات الناجحة، وما بقي خارج النطاق ولماذا.

## المخاطر والافتراضات

| الموضوع | التعامل المخطط |
|---|---|
| اختبار الأدوار المصدقة | يستخدم حسابات اختبار مخولة موجودة وبيانات آمنة فقط. إن لم تتوافر، يوثق النقص ولا يخترع حساباً أو يتجاوز الحماية. |
